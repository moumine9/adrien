## Context

Releases go to npm from a protected `main`, and the project is public, so users read what changed. A changelog written by hand at release time gets skipped, and one generated from commit messages is only as good as those messages.

## Considered options

- No changelog, relying on GitHub release notes.
- A hand-written `CHANGELOG.md`.
- A `CHANGELOG.md` generated by conventional-changelog from Conventional Commits, with a CI check that a version has an entry.

## Decision

`CHANGELOG.md` is generated at release time by `pnpm changelog` (conventional-changelog, `conventionalcommits` preset) from the commits since the last `v*` tag. `pnpm changelog:check` fails when the version in `packages/cli/package.json` has no non-empty entry. CI runs it on every push and pull request, and the release workflow runs it before publishing, so a version change cannot be merged or released without an entry.

## Consequences

Commit subjects are public text and must be written for readers. Because releases are merge commits, the tool cannot split older releases by tag, so each release adds only the section since the previous tag and the first releases are summarised by hand. The check looks only at the current version, so it needs no base branch, but it cannot tell whether an entry is accurate.
